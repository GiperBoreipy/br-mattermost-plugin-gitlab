# План доработок GitLab-плагина — WEB-2357

Задача: https://jira.blackhub.team/browse/WEB-2357

## Уточнённые требования

- Дубли — два сообщения в личке с GitLab-ботом: уведомление по подписке на репозиторий и автоматическое персональное уведомление.
- Доступа к установленному плагину и истории доставок webhook сейчас нет. Диагностика и разработка выполняются по текущему коду и локальным тестам; проверка работающей установки потребуется позднее.
- Документацию пока никуда не публикуем.

## Статус реализации

Локальная реализация этапов 1–4 завершена. Инструкция: [GITLAB_GUIDE_RU.md](GITLAB_GUIDE_RU.md). Прошли Go-тесты с `-race`, `make check-style`, frontend-тесты (46), production-сборка webapp. У webpack остаются предупреждения о размере bundle. Проверки установленной системы и взаимодействия с внешним сокращением ссылок остаются открытыми.

## Исходное поведение до доработки

- Подписка сохраняет текущий `ChannelID`, в том числе канал лички с ботом (`server/subscriptions.go`).
- Обработчики MR и комментариев независимо формируют уведомления для пользователей и каналов (`server/webhook/merge_request.go`, `server/webhook/note.go`).
- Персональные уведомления отправляются в личку с ботом через `CreateBotDMPost` (`server/plugin.go`). Поэтому обе ветки могут иметь один фактический канал назначения.
- В `server/webhook.go` уже есть атомарная дедупликация с TTL 30 секунд. Для персональных и канальных сообщений используются разные ключи, зависящие от текста. Разные представления одного события она не объединяет.
- Повторяющиеся получатели очищаются внутри одного обработчика, но не объединяются между независимыми обработчиками.
- Название MR сейчас доступно в tooltip при наведении (`webapp/src/components/link_tooltip/index.tsx`). Источник замены URL на `BRClient:MR-2639` в текущем репозитории не найден.
- В модели подписки нет фильтров по изменённым файлам (`server/subscription/subscription.go`).

Причина дублей описана как сценарий, подтверждённый устройством текущего кода. На установленной версии она пока не воспроизведена.

### 1.2. Формировать конечные доставки до отправки

- [x] В обработке webhook определить фактические каналы назначения персональных уведомлений.
- [x] Собрать уведомления одного события и объединить доставки в один конечный канал независимо от текста и источника.

Предлагаемое правило выбора итогового сообщения:

1. Явное упоминание приоритетнее обычного персонального уведомления.
2. При пересечении подписки и обычного персонального уведомления оставлять сообщение подписки как более подробное.
3. При пересечении подписки и упоминания сохранить смысл упоминания и необходимый контекст события, включая текст комментария.

Конкретный формат объединённого сообщения закрепить тестами при реализации. Для выбора не сравнивать готовые строки: при необходимости расширить внутреннюю модель уведомления признаком его назначения.

## Этап 3. Добавить фильтры подписок по файлам и папкам

### Семантика фильтров

- Пути задаются относительно корня репозитория.
- Точный файл требует точного совпадения; папка включает все вложенные файлы.
- Несколько путей объединяются через ИЛИ.
- Условия по событию, labels и путям объединяются через И.
- Для комментария проверяется набор изменённых файлов всего MR, а не только файл обсуждения.
- При переименовании учитываются старый и новый пути.
- Подписки без фильтров путей продолжают работать как раньше.

### Реализация

- [x] Расширить команду создания подписки, вывод списка, API и боковую панель.


- [x] Добавить получение изменённых файлов MR через GitLab API с пагинацией и проверкой полноты результата.
