# GitLab в Mattermost: подписки и уведомления

Локальный исходник инструкции для WEB-2357. Примеры соответствуют командам и локальным тестам этой версии. Проверка установленного плагина и используемых клиентов Mattermost ещё требуется.

## Подключение аккаунта

Выполните в Mattermost:

```text
/gitlab connect
```

Откройте предложенную ссылку и разрешите доступ к GitLab. Проверить подключённый аккаунт:

```text
/gitlab me
```

Настройки персональных уведомлений:

```text
/gitlab settings notifications on
/gitlab settings notifications off
```

Отключение персональных уведомлений не удаляет подписки канала, включая подписки в личке с GitLab-ботом. Автор события не получает автоматическое персональное уведомление о собственном действии. Подписка канала при этом может сработать.

Для отключения аккаунта используйте `/gitlab disconnect`. Напоминания управляются отдельно: `/gitlab settings reminders on` и `/gitlab settings reminders off`.

## Подписки на проект и группу

Команды относятся к **каналу, в котором выполнены**. Для подписки в личке откройте диалог с GitLab-ботом и выполните команду там.

MR и комментарии проекта:

```text
/gitlab subscriptions add client/BRClient merges,merge_request_comments
```

Подписка на группу:

```text
/gitlab subscriptions add client merges,merge_request_comments
```

Групповая подписка применяется к проектам непосредственно в этом namespace. Для проекта `client/tools/Editor` используйте группу `client/tools` или сам проект; подписка `client` не наследуется автоматически всеми подгруппами.

Просмотр и удаление:

```text
/gitlab subscriptions list
/gitlab subscriptions delete client/BRClient
/gitlab subscriptions delete client
```

Повторное `add` для того же проекта или группы в том же канале **заменяет** подписку целиком, включая события, labels, пути и создателя. Для изменения фильтра передавайте полный новый набор параметров. Подписки проекта и группы существуют независимо.

Без списка событий используется `merges,issues,tag`. При создании и доставке действуют ограничения namespace и проверки прав плагина. Для приватного проекта создателю подписки нужен доступ выше Guest. Для публичного проекта без конфиденциального содержимого членство необязательно; запрос diff всё равно выполняется от создателя подписки.

## События и labels

Основные события:

| Параметр | Содержимое |
| --- | --- |
| `merges` | Создание, закрытие, повторное открытие, слияние, approve/unapprove MR и изменения исполнителей, поддерживаемые обработчиком |
| `merge_request_comments` | Комментарии к MR |
| `merge_request_assigns` | Назначение и снятие исполнителей MR |
| `issues`, `issue_comments`, `issue_assigns` | События задач GitLab |

Остальные события перечислены в `/gitlab help`.

Несколько labels задаются повторением `label:`. Совпадения хотя бы одной метки достаточно:

```text
/gitlab subscriptions add client/BRClient merges,merge_request_comments,label:"review",label:"Editor Team"
```

Для MR-комментария проверяются labels самого MR. Отсутствующая метка исключает доставку по этой подписке.

## Фильтры файлов и папок

```text
/gitlab subscriptions add client/BRClient merges,merge_request_comments,path:"Assets/Editor/",path:"ProjectSettings/ProjectSettings.asset"
```

Правила:

- Пути относительно корня репозитория, с `/` в качестве разделителя.
- `path:"Assets/Editor/"` — папка со всеми вложенными файлами. Завершающий `/` обязателен для обозначения папки.
- `path:"ProjectSettings/ProjectSettings.asset"` — точный файл.
- Несколько путей объединяются через **ИЛИ**.
- События, labels и пути объединяются через **И**.
- `src/` не совпадает с `src-old/`; регистр символов учитывается.
- При переименовании проверяются оба пути: старый и новый. Создание и удаление файла тоже учитываются.
- Для любого комментария используется список файлов **всего MR**, даже если комментарий не привязан к файлу.
- Без `path:` подписка работает по прежним правилам.

Пример: события MR с меткой `Editor` и изменениями в папке редактора:

```text
/gitlab subscriptions add client/BRClient merges,merge_request_comments,label:"Editor",path:"Assets/Editor/"
```

Пути должны быть заключены в двойные кавычки. Запрещены абсолютные пути, `.`/`..`, пустые сегменты, обратный слеш, переносы строк и запятые. Wildcards и glob-шаблоны не поддерживаются. Одиночные пробелы внутри кавычек поддерживаются; slash-команда нормализует последовательности пробельных символов.

Пути поддерживаются только совместно с `merges`, `merge_request_comments`, `merge_request_assigns` и необязательными `label:`. Для других событий, включая `confidential_issues`, создайте отдельную подписку в другом канале либо используйте подписку без путей.

Подписки с путями требуют GitLab API `GET /projects/:id/merge_requests/:iid/diffs` (GitLab 15.7+). Плагин получает все страницы и сверяет число файлов с `changes_count`, затем проверяет, что MR не изменился во время чтения. Неизвестное/ограниченное число файлов, несовпадение количества, изменение MR или ошибка API означают **отказ доставки по подписке с путями**. Уведомления без путей и персональные уведомления продолжают обрабатываться независимо.

Список файлов запрашивается только для подписок, прошедших фильтры события и labels. В пределах события результат переиспользуется для подписок одного создателя; между разными создателями результат не разделяется.

Фильтры отображаются в `/gitlab subscriptions list`, а также в боковой панели в секции **Files and folders (MR)**. API списка подписок дополнительно возвращает `paths`; исходная строка `features` сохраняет `path:` для совместимости.

## Как объединяются сообщения в личке

Для одного webhook сначала вычисляются все подходящие уведомления и реальные каналы назначения. На один конечный канал создаётся один пост:

1. При пересечении обычного персонального уведомления и подписки остаётся подробное сообщение подписки.
2. Явное упоминание имеет приоритет над обычным персональным уведомлением.
3. При пересечении упоминания и подписки один пост содержит блок упоминания, затем контекст подписки. Текст комментария сохраняется; он может присутствовать в обоих блоках.
4. Пересекающиеся подписки проекта и группы не создают два одинаковых поста в том же канале.
5. Доставка в другой канал остаётся независимой.

Само наличие подписки не подавляет персональное уведомление: подписка должна пройти проверки прав, события, labels и путей. Отключение персональных уведомлений отключает также блок упоминания, но не подходящую подписку.

## Название MR в ссылке

Обычная ссылка на MR при отправке превращается в Markdown-ссылку с видимым названием:

```text
[BRClient:MR-2639: feature: TOOLS-1005 World Editor](исходный URL)
```

Поддерживаются подгруппы, несколько ссылок, query-параметры и `#anchors`. Заголовок экранируется для Markdown. Преобразование работает независимо от настройки превью кода и использует токен отправителя, без повышения прав.

Ссылки с собственным текстом (`[мой текст](URL)`), изображения, code blocks и inline code сохраняются. При редактировании преобразуются только новые обычные ссылки: уже сформированные подписи не обновляются при переименовании MR в GitLab. Повторная обработка не вкладывает Markdown-ссылки друг в друга.

Общий таймаут запросов заголовков на сообщение — 2 секунды. При отсутствии подключения, истёкшем токене, отказе доступа или ошибке API ссылка сохраняется исходной. В hook отправки истёкший токен не обновляется, чтобы не ждать блокировку обновления токенов. При необходимости проверьте подключение и повторите отправку ссылки.

Источник сокращения вида `BRClient:MR-2639` в исходном коде до этой доработки не обнаружен. На установленной системе отдельно проверьте порядок обработки ссылок другими плагинами и фактический рендеринг клиентов.

## Диагностика

### Нет уведомления

1. `/gitlab me`: подключён ли нужный GitLab-аккаунт?
2. `/gitlab settings notifications on`: включены ли персональные уведомления? Не является ли пользователь отправителем события?
3. `/gitlab subscriptions list` в нужном канале: правильны ли namespace, события, labels и пути? Не была ли подписка заменена повторным `add`?
4. Есть ли у создателя подписки доступ к проекту и diff? Проходят ли ограничения приватных репозиториев и namespace?
5. `/gitlab webhook list client/BRClient`: установлен ли hook с нужными событиями? Для комментариев требуется событие Comments/Note.
6. В логах ищите `path filter skipped`, `incomplete MR diff`, `incomplete MR changes count`, `MR changed while reading diffs`, `can't resolve webhook DM channel`, `can't create post for webhook event`.

### Повторные webhook и дубли

Дедупликация использует атомарный KV-ключ «идентичность события + конечный канал» со сроком хранения **24 часа** и работает между экземплярами плагина. Для MR и комментариев идентичность вычисляется из канонических данных payload: проекта, object attributes (включая ID комментария, action и timestamps), changes и автора события. Идентификатор конкретного hook не используется: project/group hooks одного действия должны объединяться. Для событий без object attributes fallback — хеш исходного payload. Два отдельных комментария с одинаковым текстом имеют разные ID и доставляются независимо.

Выбор идентичности сверён с [документацией GitLab по delivery headers](https://docs.gitlab.com/user/project/integrations/webhooks/#delivery-headers): `X-Gitlab-Webhook-UUID` относится к конкретному hook; `X-Gitlab-Event-UUID` может повторяться у рекурсивных событий; `Idempotency-Key` появился в 17.4 и стабилен при повторах доставки, а `webhook-id` появился в 19.0 и равен `Idempotency-Key`. Эти заголовки не используются как единственный общий ключ project/group hooks. Выбранная идентичность MR/комментариев работает и без новых заголовков. Ожидается стандартный полный webhook payload, без пользовательского шаблона, удаляющего ID, action и timestamps.

- При ошибке KV доставка продолжается с предупреждением `failed to claim dedup key, delivering anyway`; защита от повторов в этом случае не гарантируется.
- При ошибке разрешения DM-канала ключ не захватывается: повтор webhook может доставить сообщение.
- При ошибке создания поста ключ сохраняется до истечения TTL: Mattermost мог сохранить пост до ошибки ответа. Поэтому автоматический повтор в течение суток может быть пропущен, даже если пост фактически не создался.
- После истечения TTL старый webhook может снова создать пост. Это ограниченная дедупликация, а не бессрочная история доставок.

Для проверки установленной системы нужны версия плагина (`/gitlab about`), project/group hooks, история webhook-доставок, ID событий и каналов. Секрет webhook и OAuth-токены в диагностические материалы не включайте.

## Проверка перед выпуском

Локальные проверки:

```sh
make apply
go test -race ./server/...
make check-style
cd webapp
npm run test-ci
npm run build
```

На работающей установке ещё необходимо сверить версию плагина, проверить одну тестовую личку и отдельный канал, пересечение project/group hooks, внешний вид ссылок в используемых клиентах и фильтры на тестовом MR. Эта инструкция подготовлена локально; публикация в БЗ отложена.
